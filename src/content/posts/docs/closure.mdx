클로저는 함수가 자신이 선언된 렉시컬 환경을 기억하는 것이다. 그래서 외부 함수의 실행 컨텍스트가 종료된 뒤에도 내부 함수는 외부 함수의 변수에 접근할 수 있다.  
내부 함수는 자신이 선언된 렉시컬 환경에 대한 참조를 함께 가지는데, 그 함수에 도달 가능한 참조가 남아 있는 동안은 외부 변수도 GC되지 않는다.

## 예시

```typescript
function outer() {
	const x = 10;

	function inner() {
		// 클로저
		console.log(x);
	}

	return inner;
}

const fn = outer(); // outer 실행 종료
fn(); // 10
```

`outer`의 실행이 끝났는데도 `fn()`을 호출하면 x를 읽을 수 있다.

### 원리

- 함수는 생성될 때 자신이 선언된 렉시컬 환경에 대한 참조를 함께 가진다. 스펙에서는 함수 객체의 `[[Environment]]` 내부 슬롯이 이 참조를 담당한다.
- `outer`의 실행 컨텍스트는 종료되어 콜 스택에서 사라지지만, 그 렉시컬 환경은 `inner`가 참조하고 있기 때문에 GC되지 않고 남는다.

## 클로저를 사용하는 이유

### 데이터 은닉(캡슐화)

외부에서 직접 접근하면 안되는 상태를 감추고, 정해진 인터페이스로만 접근 가능하게 만든다.

```typescript
function createCounter() {
	let count = 0; // 외부에서 직접 접근 불가

	return {
		increment() {
			count++;
		},
		getCount() {
			return count;
		},
	};
}

const counter = createCounter();
counter.increment();
counter.increment();
console.log(counter.getCount()); // 2
console.log(counter.count); // undefined
```

`count`는 `createCounter` 스코프 안에만 존재하고, 반환된 메서드를 통해서만 접근할 수 있다.

### 설정 값을 기억하는 함수(부분적용 / 커링)

같은 로직에 다른 설정을 입힌 함수를 여러 개 만들 수 있다.

```typescript
function makeAdder(x) {
	return function (y) {
		return x + y;
	};
}

const add5 = makeAdder(5);
const add10 = makeAdder(10);

console.log(add5(3)); // 8
console.log(add10(10)); // 20
```

`makeAdder(5)`를 호출하는 순간 새로운 렉시컬 환경이 만들어지고 그 환경에는 `x = 5`가 저장된다. 반환된 함수는 이 환경을 기억하는 클로저이므로, 나중에 `add5(3)`을 호출해도 `x`가 5로 남아 있다.  
`makeAdder(10)`은 완전히 별개의 호출이라 또 다른 렉시컬 환경을 만들고, 그 안에는 `x = 10`이 저장된다.  
`add5`와 `add10`은 같은 코드로 만들어졌지만 서로 다른 환경을 참조하는 별개의 클로저라 각자 다른 `x`를 기억한다.

커링은 인자를 여러 개 받는 함수를 인자를 하나씩만 받는 함수의 체인으로 바꾸는 것이다.

```typescript
function curry(a) {
	return function (b) {
		return function (c) {
			return a + b + c;
		};
	};
}

curry(1)(2)(3); // 6

const addTo1 = curry(1); // a = 1을 기억하는 클로저
const addTo1And2 = addTo1(2); // a = 1, b = 2를 기억하는 클로저
console.log(addTo1And2(3)); // 6
```

`curry(1)`을 호출하면 `a = 1`을 기억하는 클로저가 반환된다. 그 클로저를 `(2)`로 호출하면 `a`와 `b`를 기억하는 또 다른 클로저가 반환된다.
이런 식으로 호출할 때마다 이전 인자들을 계속 기억하는 새 클로저가 만들어지고, 마지막 함수가 호출되는 순간 누적된 `a`, `b`, `c`를 모두 이용해 결과를 계산한다.  
즉 커링은 클로저를 여러 겹 쌓아서 인자를 하나씩 누적하는 기법이며, 각 겹이 유지되는 이유가 바로 클로저의 렉시컬 환경 참조이다.

### 이전 호출 상태 기억

타이머 id처럼 호출 사이에 유지되어야 하는 값을 클로저로 들고 있는다.

```typescript
function debounce(fn, delay) {
	let timer; // 호출 사이에 유지되는 상태

	return function (...args) {
		clearTimeout(timer);
		timer = setTimeout(() => fn(...args), delay);
	};
}

const onSearch = debounce((keyword) => {
	console.log('검색:', keyword);
}, 300);

onSearch('a');
onSearch('ab');
onSearch('abc'); // 300ms 뒤 '검색: abc' 한 번만 실행
```

각 호출 사이에 값이 유지될 수 있는 이유는 다음과 같다.

우선 `debounce(fn, delay)`는 한 번만 호출된다. 그 호출로 하나의 렉시컬 환경이 만들어지고, 그 안에 `timer` 변수가 저장된다.
이후 익명함수(클로저)가 반환되어 `onSearch`에 할당되는데, `onSearch('a')`, `onSearch('ab')`, `onSearch('abc')`는 모두 같은 함수를 반복 호출 하는 것이다.
같은 함수이므로 그 함수가 참조하는 렉시컬 환경도 매번 동일하다. 즉 호출마다 새 환경이 만들어지는 게 아니라, 하나의 환경을 계속 재사용하기 때문에 timer에 담긴 값이 다음 호출까지 그대로 이어진다.

이 지점이 부분 적용과 다른 점이다. `makeAdder(5)`처럼 바깥 함수를 다시 호출하면 그때마다 새 환경이 생기지만,
`onSearch`는 바깥 함수(`debounce`)를 다시 호출하는 게 아니라 이미 만들어진 반환값을 재호출하는 것이므로 환경이 계속 공유된다.

그래서 동작 순서는 이렇게 된다.

1. `onSearch('a')` 호출 → 아직 실행 중인 타이머 없음 → 새 타이머 설정, timer에 저장
2. `onSearch('ab')` 호출 → 같은 환경의 timer를 읽어 clearTimeout으로 취소 → 새 타이머 설정, timer를 덮어씀
3. `onSearch('abc')` 호출 → 마찬가지로 이전 타이머 취소 후 새로 설정
4. 300ms 동안 추가 호출이 없으면 마지막에 설정된 타이머가 실행되어 'abc'만 출력

`timer`를 전역 변수로 뒀다면 여러 개의 `debounce` 인스턴스가 서로의 타이머를 덮어쓰는 문제가 생긴다. 클로저 덕분에 `timer`가 `debounce`의 각 반환 함수별로 격리되면서도, 그 함수가 호출되는 동안에는 값이 유지된다.

### 콜백에서 등록 시점의 문맥 유지

비동기 콜백이나 이벤트 핸들러가 나중에 실행될 때도, 등록된 시점의 변수에 접근할 수 있다.

```typescript
function setupButtons(buttons) {
	for (let i = 0; i < buttons.length; i++) {
		buttons[i].addEventListener('click', () => {
			console.log(`${i}번 버튼 클릭`);
		});
	}
}
```

클릭은 한참 뒤에 일어나지만, 각 핸들러는 자신이 만들어질 때의 `i` 값을 기억한다. 여기서 주의할 점은 `let` 대신 `var`를 쓰면 모든 핸들러가 같은 `i`를 공유해서 문제가 된다.

```typescript
for (var i = 0; i < 3; i++) {
	setTimeout(() => console.log(i), 0);
}
// 3, 3, 3
```

- `var`는 함수 스코프라서 `i`에 대한 바인딩(변수와 값을 연결하는 단위)이 반복문 전체에서 하나만 존재하고, 콜백 3개가 모두 그 하나의 바인딩을 참조한다.
- `setTimeout`은 비동기라 반복문이 끝나 `i`가 3이 된 뒤에 실행된다.
- `let`은 `for`문에서 반복마다 새로운 바인딩을 생성하도록 명세에 정의되어 있다. 각 반복은 이전 반복의 값을 복사해 이어받는 새 바인딩에서 실행되므로, 콜백 3개가 각각 서로 다른 바인딩을 참조해 0, 1, 2가 나온다.

### React hooks

`useEffect`의 콜백이나 이벤트 핸들러가 렌더 시점의 state와 props를 기억하는 것도 클로저 덕분이다.
컴포넌트 함수는 렌더마다 새로 호출되고, 그 때마다 `count`라는 지역 변수가 새로운 렉시컬 환경에 새로 만들어진다.
그 안에서 선언한 함수는 해당 렌더의 렉시컬 환경을 참조하는 클로저이므로, 렌더 시점의 `count`값을 계속 기억한다.

```typescript
function Counter() {
	const [count, setCount] = useState(0);

	const handleClick = () => {
		setCount((c) => c + 1);
		setTimeout(() => {
			alert(`count: ${count}`);
		}, 3000);
	};

	return <button onClick={handleClick}>+</button>;
}
```

버튼을 클릭하면 `count`가 1 증가하지만, 3초 뒤에 표시되는 `alert`에는 클릭이 일어난 렌더 시점의 count 값인 0이 출력된다.
이유는 `setTimeout` 안의 콜백 함수가 그 렌더의 렉시컬 환경을 참조하고, 그 환경의 `count`는 0이기 때문이다. `setCount`로 발생한 다음 렌더는 `count = 1`인 별개의 렉시컬 환경을 만든다.

## 주의할 점

### 메모리 누수

클로저 자체가 메모리 누수는 아니다. 문제는 더 이상 필요 없는 클로저에 도달 가능한 참조 경로가 남아 있어, GC가 그 클로저를 회수 대상에서 제외할 때 발생한다.

```typescript
function startPolling() {
	const cache = new Array(100000).fill(0);

	setInterval(() => console.log(cache.length), 1000);
}

startPolling(); // startPolling 실행은 끝났지만, cache는 여전히 메모리에 남아 있다.
```

`startPolling()`의 호출 자체는 끝나서 콜 스택에서 사라지지만, `cache`는 정리되지 않는다.
그 이유는 브라우저 타이머 목록에서 `setInterval`의 콜백을 참조하고 있고, 그 콜백에서는 `cache`를 참조하고 있기 때문이다.
즉 브라우저 타이머 목록에서 `cache`까지 도달 가능하기 때문에 GC되지 않고 메모리에 남아있게 된다.

### 해결 - 참조 끊기

```typescript
function startPolling() {
	const cache = new Array(100000).fill(0);

	const id = setInterval(() => console.log(cache.length), 1000);
	return () => clearInterval(id);
}

const stop = startPolling();
stop(); // 더 이상 필요 없을 때 호출
```

`clearInterval`이 실행되면 브라우저 타이머 목록에서 콜백에 대한 참조가 제거된다. 그 결과, 콜백에 대해 도달 가능한 경로가 사라지고, 콜백과 그 콜백이 캡처하고 있던 `cache`가 함께 GC된다.
